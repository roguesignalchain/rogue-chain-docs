# RandomX 种子纪元与延迟机制

RandomX 算法依赖一个由区块链历史状态派生而来的伪随机密码学密钥（**种子哈希 Seed Hash**）来生成其高达 2080 MiB 的内存计算数据集。为了保证全网所有节点之间的绝对确定性，Rogue Signal 引入了严谨的周期性种子轮换机制。

---

## 🔄 种子纪元时间表与核心参数

| 参数项 | 数值 | 详细说明 |
| :--- | :--- | :--- |
| **纪元持续周期** | `2048 个区块` | 种子哈希更新的区块跨度（按 30 秒出块，约 17.07 小时） |
| **种子延迟（Seed Lag）** | `64 个区块` | 安全缓冲窗口（~32 分钟），防止数据集生成时的竞态停顿 |
| **数据集容量** | `2080 MiB` | 驻留在系统 RAM 中的高速数据集（由 `runtime.NumCPU() / 2` 协程初始化） |
| **暂存器容量（Scratchpad）** | `2 MiB` | 每个挖矿执行线程独占的 CPU L3 缓存内存空间 |

---

## 🛡️ 64 区块延迟与防重组种子机制

即使在现代多核处理器上，构建完整的 RandomX 随机数据集也需要数秒甚至更长时间。若直接取前一个区块（`H-1`）作为新纪元的种子哈希，节点将在切换瞬间遭遇严重的计算停滞并错失出块机会。

为了彻底解决此问题：
* 在始于 `H = E * 2048` 的纪元 `E` 中，其种子哈希由以下历史区块高度的规范区块哈希计算得出：
  ```text
  种子区块高度 = (E * 2048) - 64
  ```
* 这为全网所有挖矿节点与验证者提供了长达 **1,920 秒（约 32 分钟 / 64 个区块）的确定性缓冲时间窗口**，在真正进入新纪元切换点前，后台利用 `max(1, runtime.NumCPU() / 2)` 线程平滑预生成新数据集。
* **规范种子交叉校验：** 当调用 `EpochManager.GetSeed` 或 `GetContext` 时，节点会严格校验纪元 `E` 缓存的种子哈希是否与主链当前的 `chain.GetHeaderByNumber(seedBlock)` 一致。若发生深度在安全范围内的合法分叉重组并导致种子区块变更，陈旧上下文将被安全注销（受 `defer ctx.mu.RUnlock()` CGo 内存安全保护）并自动触发重新构建。
